# 仕組みの解説

> このツールが何をしているかを、コードを開かずに理解できるように書いた文書。
> 設計判断の「なぜ」は [ADR](adr/) に、「何を作るか」は [仕様書](spec.md) にある。

## 1. 全体の流れ

やっていることは、突き詰めると次の1行に尽きる。

> **動いたときに報告させ、報告が来ないことを検知する。**

動かなかったものは、自分では何も言えない。だから「動いた」という報告の**不在**を見る。

```
① 処理する側が「動いた」と記録する        journal.ts
② 見張る側が「直近で動くはずだった時刻」を求める  schedule.ts
③ その時刻より後に報告があるかを見る        check.ts
④ まだ知らせていない異常だけを取り出す       check.ts（pendingAlerts）
```

## 2. ファイルごとの役割

| ファイル | 役割 |
|---|---|
| `types.ts` | 言葉の定義。処理は書かない |
| `calendar.ts` | 営業日かどうかの判定。祝日の一覧は持たない |
| `schedule.ts` | 「直近で動くはずだった時刻」を求める。ここが計算の中心 |
| `journal.ts` | 報告の置き場所（メモリ / ファイル） |
| `check.ts` | 判定と、通知の重複抑制 |

## 3. 判定の考え方

```
直近で動くはずだった時刻（occurrence）を求める
    ↓
報告が1件も無い            → never_ran（仕掛け忘れの可能性）
最後の報告が occurrence 以降 → ok / failed
それ以外で、遅れが猶予以内   → late
それ以外                  → missing  ← 本題
```

`never_ran` と `missing` を分けているのは、**原因も打つ手も違う**ため。前者は仕掛けを入れ忘れており、後者は動いていたものが止まっている。

## 4. 説明できるようにしておきたい設計判断

### 判断1: 見張り番は監視対象と同じ場所に置かない

同じサーバーに置くと、サーバーごと落ちたときに見張りも一緒に死ぬ。**最も検知したい状況こそ、見張り番が動かない状況になる。**

この誤りは実際に起きた。ある週次の自動処理が通信断で失敗し、**4日間、誰にも気づかれずに放置された**。成否を確認していたのが、同じ仕組みの中の自己申告だけだったためである。

> **実行できたかどうかを、実行する側に聞いてはいけない。**

そのために、この道具は「監視対象を呼ばない」「現在時刻を引数で受け取る」「記録の置き場所を差し替えられる」の3つを守っている。

> 聞かれたら: 「見張りを同じサーバーに置くと、サーバーが落ちたとき見張りも止まります。だから外から見る前提で作りました」

### 判断2: 現在時刻を内部で読まない

`check()` は `now` を引数で受け取る。内部で `new Date()` を呼ばない。

これには2つの効果がある。

1. **別の場所・別の時刻から実行しても、同じ記録なら同じ判定になる**（判断1の前提）
2. **テストで時刻を自由に決められる。** 「9/11 10:00 時点ではこう判定される」を固定できる

時刻を内部で読む設計にすると、深夜0時をまたぐ挙動や、月末の挙動をテストできなくなる。

### 判断3: 祝日の一覧を内蔵しない

日本の祝日は法律で変わる（山の日の新設、五輪に伴う移動）。しかも企業ごとに休業日が違う（不動産は水曜定休が多い）。

内蔵すると、**ライブラリを更新しない限り、来年から静かに間違い始める。** しかも間違いに気づくのは「祝日に通知が飛んだ」ときで、そのときには信頼を失っている。

だから一覧は利用者が渡す。代わりに、**一覧が古くなっていることに先に気づける仕掛け**を入れた（未来の休業日が1件も無ければ警告する）。

> 聞かれたら: 「祝日は法律で変わるので、内蔵すると必ず古くなります。渡してもらう代わりに、古くなったことに気づける警告を入れました」

### 判断4: 同じ欠測で鳴り続けない

止まっている間ずっと通知すると、担当者は通知を切る。**通知を切られたら、この道具は存在しないのと同じになる。**

予定時刻ごとに鍵を作り、その鍵で「知らせたか」を記録する。翌日また欠測すれば別の鍵になるので、改めて知らせる。

### 判断5: 通知そのものは持たない

判定を返すだけで、メールもSlackも送らない。送信手段を抱えると、送信先の都合で本体を変えることになる。

## 5. 想定問答

**Q. 監視ツールは既にあります（Datadog、Mackerel など）。何が違うのですか？**
それらでも死活監視はできます。この道具が絞っているのは「**定時に動くはずのものが動かなかった**」という一点です。特に、日本の営業日（水曜定休や祝日）を扱えること、通知が鳴り続けないことに寄せてあります。既存の監視と併用できます。

**Q. 見張り番が止まったら意味が無いのでは？**
そのとおりです。原理的に解決しません。だからREADMEに限界として書き、置き場所の推奨（GitHub Actions などの外部サービス）を示しています。「完全に監視できます」と言うほうが危険だと考えています。

**Q. cron 式に対応しないのはなぜですか？**
`0 6 * * *` は読み間違えても気づけないからです。`dailyAt("06:00")` なら読んで分かります。複雑なスケジュールが必要なら、この道具は向いていません。

**Q. 記録はどこに置きますか？**
報告する側と見張る側の両方から読める場所です。同じサーバー内ならファイルで足りますが、外から見張るなら共有できる場所（ネットワーク上のディスク、データベース、オブジェクトストレージ）に `Journal` を実装し直します。インターフェースは4つのメソッドだけです。

**Q. 記録の書き込みが失敗したらどうなりますか？**
動いたジョブが `missing` に見えます。記録の置き場所の可用性に依存する、という限界がありREADMEに書いています。

**Q. 秒単位の精度は必要ないのですか？**
定時処理の見張りでは分単位で足ります。秒単位が必要な用途（リアルタイム処理の監視）は、この道具の対象外です。

**Q. テストは何を担保していますか？**
45件のテストが、予定時刻の計算（毎日・N分ごと・毎週）・営業日の扱い・判定の6種類・通知の重複抑制・記録の読み書きを押さえています。加えてCIで、不動産会社の定時処理を見張る例が最後まで動くことを毎回確認しています。
