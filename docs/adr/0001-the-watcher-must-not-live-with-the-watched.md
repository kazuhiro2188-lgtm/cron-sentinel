# ADR-0001: 見張り番は、監視対象と同じ場所で動かさない

- 状態: 採用
- 日付: 2026-09-08

## 背景

「定時処理が動いたか」を見張る仕組みを、監視対象と同じサーバー・同じプロセスに置くのは自然に思える。実装も簡単で、設定も1箇所で済む。

**しかし、それでは肝心の場面で動かない。**

サーバーが落ちれば、定時処理も見張り番も一緒に落ちる。ネットワークが切れれば、両方とも報告できない。**最も検知したい状況こそ、見張り番が動かない状況である。**

この設計の誤りは、実際に起きている。ある週次の自動処理が API の接続断で失敗し、**4日間、誰にも気づかれずに放置された**。理由は単純で、その処理の成否を確認していたのが、同じ仕組みの中の「自己申告」だけだったためである。

> 実行できたかどうかを、実行する側に聞いてはいけない。

## 決定

**見張り番は、監視対象と独立した場所で動かす前提で設計する。**

そのために次を守る。

1. **見張り番は監視対象を呼ばない。** 記録（報告の履歴）だけを読む
2. **判定は時刻を引数で受け取る。** 内部で `new Date()` を呼ばない。別の場所・別の時刻から実行しても、同じ記録なら同じ判定になる
3. **記録の置き場所を差し替えられる。** 監視対象と見張り番が別のサーバーにあるなら、共有できる場所（データベース、オブジェクトストレージ）に置ける

置き場所の推奨は文書に明記する。

| 置き場所 | 評価 |
|---|---|
| 監視対象と同じサーバー | ✗ 同時に落ちる。**最も検知したい場面で機能しない** |
| 別のサーバー | △ そのサーバーも落ちうるが、同時に落ちる確率は下がる |
| GitHub Actions などの外部サービス | ○ 自社の障害と独立している |

## 結果

### 得るもの

- サーバーが落ちても、外部から見張っていれば検知できる
- 判定が決定論的になる。「この記録とこの時刻なら、この判定」がテストで固定できる
- 見張り番の実装が小さくなる（実行も通知もしない）

### 失うもの・引き受ける限界

**見張り番自身が止まった場合は検知できない。** この問題は原理的に解決しない。見張り番を見張る仕組みを作れば、今度はそれを見張る必要が出る。無限に続く。

できるのは「止まりにくい場所に置く」ことだけである。**この限界を隠さず文書に書く。** 「完全に監視できます」と言うほうが、利用者を危険にさらす。

## 却下した案

| 案 | 却下理由 |
|---|---|
| 監視対象のプロセス内に常駐させる | サーバーごと落ちたら一緒に死ぬ。事故の原因そのもの |
| 定時処理の最後に「自分が動いた」と通知させる | 動かなかったときは通知も来ない。**不在を検知できない** |
| 見張り番を二重化して互いに監視させる | 両方が同じ理由で落ちる（同じサーバー、同じ回線）ことが多く、複雑さに見合わない |
